# 服务器推理与机器人本机执行：最小版本

新克隆或在机器人端首次安装时，先按 [仓库与两端部署](仓库部署.md) 准备对应环境。无历史实验文件也可运行 `python scripts/smoke_deployment.py --output outputs/first_transport` 验证通信，使用人工数据且不推理抓姿。

本版本先支持已知杯子、静止单物体桌面、固定头部取帧、右臂与 FDH-6。服务器接收外部 RGB-D 和关节快照，估计物体位姿，取离线 Dexonomy 候选，使用 cuRobo 与 MuJoCo 副本规划，返回七阶段轨迹。本机按本地时钟插值、检查并执行，最后向服务器回传报告。

相机暂按兼容 CAM_A/B/C 的 OAK、DepthAI **2.x** 实现。Aurora 与 FDH-6 DDS 适配器基于公开接口编写，尚未连接硬件。默认所有真机动作开关关闭，未填写的手映射没有猜测值。明天主要修改配置和设备适配层，不需要重写协议或服务器算法。

## 已有与尚未验证的范围

| 部分 | 实现与验证范围 |
|---|---|
| 通信 | 实际 TCP、MessagePack 数值数组，版本/令牌/任务绑定，超时与重复任务拒绝；不接受 pickle |
| 服务器算法 | 上传的 RGB-D 分割、几何平面位姿拟合、现有 Dexonomy 候选和 cuRobo 全臂路径；没有从仿真相机取图或读取目标真值定位 |
| 规划副本 | 从上传关节状态、基座变换与桌面初始化。物体质量、摩擦和电机接触模型仍是假设，接触预演不是实际接触反馈 |
| 模拟执行器 | 仅模拟命令与关节状态跟踪，不模拟抓取物理；报告始终 `grasp_success: null` |
| OAK | 复用 `scripts/capture_oak.py`，按设备标定取内参和对齐深度；尚未连接实际 OAK |
| Aurora / 手部 DDS | 准备了可替换调用层；尚未验证交付 SDK、控制模式、手部消息布局、通道顺序和数值单位 |
| 实物定位 | 默认 `real_rgb_pose_validated: false`，需要测量真实相机中的定位误差后才允许真机执行 |

本最小版使用**几何定位**，不沿用仿真中同渲染器的颜色消歧结果；对称/遮挡物体可能定位错误。既有相机分支的 17/18 不能作为本最小版的实物成功率。首个物体必须与配置网格尺寸一致，不能拿任意外观相似杯子直接套用 GSO 模型。多物体避障、头部主动扫描的真机执行、视觉重抓和触觉反馈不在本最小版中；后续可以通过观察/设备接口扩展。

## 今天在当前服务器运行

以下在项目根目录运行。样例来自已有仿真记录，显式标记为 `simulation_replay`，不能用于真机执行。

```bash
.venv/bin/python -m gr3_grasping.deployment sample \
  --source outputs/dexonomy_scenes6_camera/coffee_mug_yaw000/plan00__yaw0__wrap_wide__coffee_mug__2_4 \
  --output outputs/deploy_input.msgpack

# 两个独立进程、实际 TCP；只验证通信和模拟执行，不进行推理。
.venv/bin/python scripts/smoke_deployment.py \
  --observation outputs/deploy_input.msgpack --output outputs/my_transport_smoke

# 完整服务器推理，包括真实 GPU cuRobo；执行端仍为 mock。
.venv-curobo/bin/python scripts/smoke_deployment.py --planner dexonomy \
  --observation outputs/deploy_input.msgpack --output outputs/my_curobo_smoke
```

每次使用新输出目录。冒烟脚本自行生成临时共享令牌和空闲端口，并在结束时停止自己的服务器进程。服务器目录保留上传观察、位姿估计、规划副本预演、cuRobo 配置和轨迹；`client/robot_report.json` 是执行回执，`client/<task_id>.jsonl` 是本机阶段与跟踪日志。

服务器推理依赖已下载的官方资产、v2 手部元数据及 v3 抓姿库。新机器需先重建这些输入或修改 `inference.candidates` 和 `inference.arm_config`，不包含在轻量机器人环境中。

## 明天分开启动两端

服务器端：

```bash
export GR3_DEPLOY_TOKEN='replace-with-a-shared-random-token'
.venv-curobo/bin/python -m gr3_grasping.deployment server \
  --output outputs/deploy_server
```

默认只监听 `127.0.0.1:5557`。从机器人计算机建立 SSH 转发后使用本机端点连接服务器；MessagePack 通道本身没有加密，令牌不能代替安全隧道。

```bash
# 在机器人计算机的独立终端运行，替换 SSH 用户和服务器地址。
ssh -N -L 5557:127.0.0.1:5557 user@server
```

机器人端首先运行只读版本探测。该命令只查询 Python 包信息，不创建 Aurora 客户端，也不发送手部命令：

```bash
python -m gr3_grasping.deployment probe
```

服务器使用已有 `.venv-curobo`。机器人端使用兼容厂商 SDK 的 Python >=3.10 环境，项目轻量侧需要 `numpy scipy PyYAML msgpack pyzmq`，另需机上厂商提供的 Aurora、FourierDDS 消息包，以及兼容的 DepthAI 2.x。可以在该环境用 `python -m pip install -e . --no-deps` 注册本项目，保留厂商要求的 `PYTHONPATH` / `LD_LIBRARY_PATH`。不要直接用服务器的 Torch/CUDA 环境覆盖机上 SDK 环境。

核对并填写现场配置后，采集真实 OAK 帧和关节快照：

```bash
python -m gr3_grasping.deployment --config configs/deployment_site.yaml record \
  --output outputs/site_observation.msgpack
```

`record` 只读相机和关节。它要求测得的固定头部外参，比较取帧前后关节状态，并检查头部位置匹配标定参考。这个简化同步方案仅适用于静止机器人，不是硬件同步。

首先只请求服务器规划，默认不打开任何执行适配器：

```bash
export GR3_DEPLOY_TOKEN='replace-with-a-shared-random-token'
python -m gr3_grasping.deployment --config configs/deployment_site.yaml client \
  --observation outputs/site_observation.msgpack --output outputs/site_plan
```

默认客户端和冒烟脚本均不调用真机。现场校验完成后，实际执行入口是同一客户端的 `--robot aurora --execute`；它仍会检查下面的本地配置和服务器给出的观察资格，不会因收到网络轨迹就直接打开 SDK。新采集、新任务必须使用新输出目录。

同一 `observation_id` 的第二次规划会被拒绝；从只规划切换到实际执行时，重新运行 `record` 生成新的观察和任务。不要把原观察文件复制改名当作新采集。

## 现场需要填写的内容

复制 `configs/deployment_mvp.yaml` 为 `configs/deployment_site.yaml`，并单独保存实测相机标定文件。原始示例没有可用于实物的默认标定。

| 配置 | 明天核对什么 |
|---|---|
| `camera.calibration_file` | OAK 光学坐标系到选定世界系的实测外参，以及固定头部参考角；内参由设备读取。示例身份矩阵不能标为已标定 |
| `scene.*` 和 `inference.perception` | 真实基座姿态、桌面高度/范围和工作区；`calibration_verified` 还要求交付模型和实物坐标链一致 |
| `aurora.groups` | SDK 中右臂、左臂、头、腰的关节顺序、单位、方向与 URDF 一致；默认名称仅为公开模型映射 |
| `aurora.required_fsm_state` | 确认可控制右臂且保持受控支撑/站立的实际状态。程序不切换 FSM，不更改 PD 增益，不控制腿部或行走 |
| `aurora.hand.*` | FDH-6 六通道顺序、SDK 上下限、状态数组偏移、每通道 `SDK值 = scale × 弧度 + offset`。非线性映射用自定义手适配器 |
| `inference.candidates` | 首个真实物体对应的正确尺寸模型和离线抓姿，当前默认仅为样例咖啡杯 |
| `inference.real_rgb_pose_validated` | 用真实 RGB-D 测量定位误差，特别检查 180° 对称歧义与坐标反向 |
| `execution.*` | 按交付硬件确认速度、关节限位、控制频率、跟踪门限和观察有效期；示例数值是开发设置 |

只有观察被标记为真实 OAK、标定与状态映射已核实、服务器真实定位已验证，并且本机映射、运动开关和当前控制状态均匹配时，才会进入实际执行。开启开关不是硬件验证的替代品。

`adapters.py` 集中维护 OAK 采集、Aurora 调用和 `Fdh6DDS`。如果交付接口不同，主要改这里。`aurora.hand_factory: "module:create_hand"` 可以加载机器人本机的替代手适配器，需实现 `read_state()`、`prepare_motion()`、`validate_command(具名弧度字典)`、`send(具名弧度字典)`。工厂只能来自本机配置，网络请求不能指定模块或执行代码。

## 执行边界

- 本机拒绝错误任务/观察、越界/超速/不连续轨迹、不同起始状态和重复执行；所有手指 SDK 目标在任何手臂指令前预检。真机任务还在 `execution.task_ledger_dir` 保存持久执行记录，更换输出目录也不能重复执行同一任务。规划冻结的头部、腰部等关节发生变化也会中止，需要重新观察和规划。
- 控制按本机时钟运行，执行期间没有服务器逐周期 RPC。服务器中断不会变成延迟到达的电机指令；如果已经开始执行，当前版本会继续本机轨迹，网络回执失败则保留本地日志。
- `--stop-file /absolute/path/STOP` 配置本地软停止文件；存在时中止轨迹。它不能替代硬件急停。跟踪超限、调度超时或控制状态改变也会中止。异常时尝试保留手部目标并保持当前臂位，不自动松手；该行为和退出后的 SDK 命令超时机制必须现场验证。
- 目前没有真实视觉提起或滑落判定，真机回执即使 `trajectory_completed: true`，也保留 `grasp_success: null`。明天先检查空载与预抓取停点，再检查闭手和低高度提升。
- 固定头部采集的坐标变换不适用于之后移动头部或基座；改变站姿、机身位置或目标位置后，需要重新观察和规划。规划副本依旧使用理想重力补偿，不能代表实机承载和动态平衡。

官方依据：[Aurora 本机客户端要求](https://support.fftai.com/gr3/getting-started/quick-start)、[手部 DDS 接口](https://support.fftai.com/gr3/modules/gr-endeffector)。
